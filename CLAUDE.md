# TripPlanner IA

Projet fil rouge : blog et planificateur de voyage basé sur les posts et avis des voyageurs. Nom de l'app : **Biirb**. Next.js (App Router) + TypeScript strict + Tailwind CSS v4, gestionnaire de paquets **npm**.

## Commandes

```bash
podman compose up   # environnement de dev conteneurisé (ou docker compose up ; voir README.md) → http://localhost:3000
npm run dev     # serveur de dev (sans Docker)
npm run build   # build de prod (lance aussi le typecheck)
npm run lint    # ESLint
```

Dans le conteneur : `podman compose run --rm app npm run <script>`.

Vérifier `npm run lint` et `npm run build` avant de considérer une tâche terminée.

## Architecture en couches (back) — à respecter

```
CLIENT / FRONTEND
   │  requête HTTP (ex. POST /api/v1/posts)
   ▼
CONTROLLER   app/api/v1/**/route.ts → server/controllers/, Server Components (pages)
   │  DTO (types inférés des schémas Zod)
   ▼
SERVICE      server/services/*.service.ts
   │  entités / paramètres de requête
   ▼
REPOSITORY   server/repositories/*.repository.ts
   │  pool `pg` (requêtes paramétrées $1, $2…)
   ▼
DATABASE     Cloud SQL (Postgres)
```

- **Controller** : valide la requête avec le schéma Zod (`schemas/`), extrait les données (params, body, searchParams), vérifie l'auth, appelle le service adapté, puis renvoie la réponse HTTP (200, 400, 401, 404…) avec un message générique en cas d'erreur. Aucune logique métier, aucun accès direct à la base.
- **Service** : contient la logique et les règles métier (calculs, transformations, vérification que l'utilisateur est propriétaire de la ressource, orchestration de plusieurs opérations). Sait *quoi* faire, pas *comment* c'est stocké : n'importe ni la base (`pg`, `server/infra/db`, `server/infra/storage`) ni rien de HTTP (`Request`, `NextResponse`, cookies, en-têtes).
- **Repository** : seul endroit qui parle à la base. Uniquement du CRUD en SQL paramétré (`$1`, `$2`… ; jamais de SQL concaténé avec une entrée), colonnes sélectionnées explicitement (jamais de hash ni de champ interne renvoyé vers le haut). Aucune règle métier.
- Les dépendances ne vont que vers le bas et sans sauter de couche : controller → service → repository → base. Un controller n'appelle jamais un repository directement ; un repository n'appelle jamais un service.
- Un fichier par ressource et par couche : `schemas/post.schema.ts`, `server/services/post.service.ts`, `server/repositories/post.repository.ts`.
- Les composants n'importent jamais `src/server` (règle ESLint) : un composant client passe par une route API, un composant serveur reçoit ses données d'une page.

Textes dans `messages/fr.json`, une clé `…Confirm` par action avec `title` (question courte : « Supprimer cette dépense ? »), `message` (ce qui va se passer, sans promesse fausse : vérifier les cascades en base) et `action` (verbe du bouton : « Supprimer », « Réimaginer », jamais « OK » ni « Confirmer »). `danger: true` pour une action destructive : bouton et pastille rouges (`error`), focus de départ sur « Retour » ; sinon accent, focus sur l'action. Icône : celle de l'action (`delete`, `block`, `logout`, `sparkles`, `refresh`…). Refus : « Retour » (jamais « Annuler », qui désigne déjà l'annulation d'un changement de Biirbou), Échap, clic sur le fond ou croix.

## Sécurité — contrôle absolu

La sécurité prime sur la rapidité de livraison. En cas de doute, demander plutôt que supposer. Signaler explicitement toute faille ou tout compromis rencontré, même hors du périmètre de la tâche.

### Must-have bootcamp (obligatoires)

Seuls les must-have sont exigés : ne pas implémenter les nice-to-have (OAuth/OIDC, MFA, RBAC granulaire, API Gateway/WAF, chiffrement au repos, Dependabot/Snyk, centralisation des logs, etc.) sauf demande explicite.

1. **Authentification & autorisation** — JWT transmis dans l'en-tête `Authorization: Bearer <token>`. Vérification du token (signature + expiration, lib éprouvée comme `jose`) dans `src/proxy.ts` (le middleware de Next 16) pour les routes privées, **et** dans chaque route handler / Server Action qui touche des données privées. Vérifier que l'utilisateur est propriétaire de la ressource qu'il modifie. Secret JWT uniquement côté serveur. Access token JWT de **1 h**, gardé **en mémoire uniquement** côté navigateur (jamais dans localStorage / sessionStorage : un script injecté ne doit pas pouvoir le lire), + **refresh token** (30 jours avec « Se souvenir de moi » ; sinon 24 h au plus et cookie de session, effacé à la fermeture du navigateur — fermer seulement l'onglet, ou un navigateur qui restaure la session, ne déconnecte pas : compromis assumé) dans le cookie **`brb_refresh` HttpOnly, SameSite=Strict, Secure en prod, Path=/api/v1/auth** : en base uniquement son empreinte SHA-256 (table `refresh_token`), rotation à chaque refresh, réutilisation d'un token déjà utilisé = révocation de toute la session, déconnexion = révocation côté serveur + cookie effacé. À chaque chargement de page, `session.ts` récupère un access token via `/auth/refresh` (verrou entre onglets). Le stockage du navigateur ne contient que le profil affiché (`brb_user`, non secret).
2. **Endpoints API** — Rate limiting anti-bruteforce sur le login (et sur `/api/v1/chat`). CORS restreint à l'URL du frontend (variable d'env), jamais `*`. L'IP du client se lit **uniquement** via `clientIp()` (`src/server/rateLimit.ts`), qui prend l'entrée de `X-Forwarded-For` ajoutée par le proxy de confiance (`TRUSTED_PROXY_HOPS`) : jamais la première entrée, que le client peut inventer. Le login est aussi limité par compte visé (email) ; un appareil où ce compte s'est déjà connecté (cookie `brb_device`, signé, lié à l'empreinte de l'email) a son propre compteur, pour qu'un tiers ne puisse pas bloquer le titulaire en remplissant celui de l'email (un nouvel appareil reste bloqué dans ce cas). Inscription : « email déjà utilisé » (409) révèle qu'un compte existe, compromis assumé (freiné par le rate limit par IP ; le fermer demanderait une vérification par email).
3. **Données sensibles** — HTTPS/TLS en production. Mots de passe hachés avec **bcrypt**, salt rounds ≥ 10. Jamais de mot de passe en clair (ni en base, ni dans les logs, ni dans une réponse).
4. **Validation des entrées** — Schéma **Zod** en allowlist (`z.strictObject`, imposé par le lint dans `schemas/`) sur toutes les entrées serveur (body, params, searchParams) : tout champ inconnu ou mal typé est rejeté immédiatement.
5. **Dépendances** — `npm audit` avant mise en ligne : zéro vulnérabilité critique tolérée.
6. **Logs & zéro fuite technique** — Logs structurés côté serveur uniquement, via `src/server/logger.ts` (`logError` / `logInfo`, champ `severity` lu par Cloud Logging, erreurs regroupées dans Error Reporting) ; jamais `console.error` directement. Alertes Cloud Monitoring par email à l'équipe : site injoignable (vérification toutes les 5 min) et log de gravité ERROR (au plus un email par heure). Le client ne reçoit que des messages d'erreur génériques : jamais de stack trace, d'erreur SQL brute ou de détail interne. Message de login générique (« identifiants invalides »).
7. **CSRF** — Le JWT est envoyé via l'en-tête `Authorization`, jamais via un cookie : les routes de l'API ne lisent aucun cookie. Seules exceptions, validées : le cookie `brb_refresh`, lu uniquement par `/auth/refresh` et `/auth/logout`, protégé par SameSite=Strict **et** une vérification de l'en-tête `Origin` (403 si absent ou différent du site) ; le cookie `brb_device` (HttpOnly, SameSite=Strict, Path=/api/v1/auth/login), lu uniquement par `/auth/login` (même contrôle de `Origin`) pour choisir son compteur de rate limit, jamais pour authentifier. Ne pas introduire d'autre cookie sans en discuter.
8. **Base de données** — Requêtes paramétrées obligatoires (ORM type Prisma ou driver préparé), jamais de SQL concaténé avec des entrées utilisateur. Utilisateur DB avec droits restreints.
9. **Durcissement serveur** — En-têtes HTTP de sécurité (équivalent Helmet, via `headers()` dans `next.config.ts` : CSP, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, HSTS). Si Docker : conteneur exécuté en utilisateur **non-root**. En place dans `next.config.ts` (`securityHeaders`, `poweredByHeader: false`) : toute nouvelle ressource externe (image, script, API) doit y être ajoutée à la CSP.
10. **Audit régulier** — Repasser régulièrement cette checklist point par point et tester l'injection d'erreurs (entrées invalides, token absent/expiré/falsifié, champs inconnus, SQL/XSS).

### Règles complémentaires
- **Variables sensibles : toujours dans le `.env` (`.env.local`, ignoré par git), jamais en dur dans le code.** Sont sensibles :
  - les **secrets** : clés et mots de passe (`JWT_SECRET`, `JWT_REFRESH_SECRET`, future clé Gemini…) ; la base Cloud SQL n'en a pas (authentification IAM) ;
  - les **réglages de sécurité** : durée du token (`JWT_EXPIRES_IN`) et des sessions (`REFRESH_TOKEN_*`), coût bcrypt (`BCRYPT_SALT_ROUNDS`), rate limits (`RATE_LIMIT_*`), et tout nouveau réglage du même type (URL autorisée par CORS…).
  Les secrets sont lus côté serveur uniquement : jamais dans une variable `NEXT_PUBLIC_*`, ni dans un composant `"use client"`, ni dans un log, une réponse d'API ou un commit. Une valeur de secret ne doit jamais apparaître dans le code, même en valeur par défaut.
  Restent dans le code (pas dans le `.env`) : les limites de données qui doivent rester identiques aux contraintes SQL de `db/migrations/` (longueur du titre, des descriptions, taille max de la photo, nombre de tags…).
- Toute variable d'environnement lue par l'app ou un script est listée dans `.env.example` (seul fichier `.env*` versionné) avec une valeur d'exemple, à quoi elle sert et quel fichier la lit. Jamais de vraie valeur dedans. Côté serveur, on les lit uniquement via `getConfig()` (`src/server/config.ts`), jamais `process.env` directement (sauf `NODE_ENV` et les scripts de `scripts/`). Un réglage de sécurité peut avoir une valeur par défaut sûre dans `config.ts` ; un secret, jamais (variable obligatoire, validée par Zod).
- Ne jamais renvoyer au client plus de données que nécessaire (pas de hash, pas de champs internes).
- Pas de `dangerouslySetInnerHTML` sur du contenu utilisateur.
- Chat RAG : traiter la question utilisateur et le contenu des posts comme non fiables (injection de prompt), limiter la taille des entrées.
- **Nom de l'IA dans l'interface : « Biirbou »** (Biirb + « -ou » affectueux ; la mascotte est un pigeon voyageur ; nom propre masculin sans article : « Générer avec Biirbou », « Biirbou réfléchit… »). Jamais « l'IA » ni « Gemini » dans `messages/fr.json`.
- IA (planificateur, chat) : Gemini via Vertex AI (`src/server/infra/ai.ts`), authentifié par IAM comme la base : aucune clé API (variables `GCP_PROJECT_ID`, `VERTEX_LOCATION`). Réponse du modèle = donnée non fiable, toujours revalidée par Zod. Tout appel à l'IA passe d'abord par `consumeAiCall` (`ai-quota.service.ts`) : **15 appels par jour et par utilisateur** (`AI_DAILY_LIMIT_PER_USER`, limites horaires `RATE_LIMIT_TRIP_AI_*` et `RATE_LIMIT_TRIP_CHAT_*` dans le .env ; admins illimités, compteur en base `ai_usage`, jour de Paris), plafond global et interrupteur réglables par l'admin (`app_settings`), compte banni refusé.
- Planificateur : départ à n'importe quelle date future, durée de 3 mois maximum **à partir du départ choisi** (`TRIP_MAX_DAYS` = 92 jours ; au-delà de 31 jours, journées moins détaillées pour tenir dans le temps de réponse de l'IA). La génération tient compte de la saison (mois du voyage) : météo moyenne, risques (typhons, mousson…), affluence et prix, résumés dans `trip.season_note`. **Plusieurs étapes** (1 à 8 pays, régions ou villes : `trip_destination`, la première reste `trip.destination_*`) : le serveur les range selon le trajet le plus court (coordonnées de country-state-city, toutes les permutations testées) avant de les envoyer à l'IA, qui suit cet ordre (ou l'inverse) sauf ordre imposé par les envies ; 15 récits envoyés : les 5 plus aimés, les 5 plus récents puis 5 au hasard (moins de 15 : tous), étapes prises à tour de rôle pour chaque critère (`postsForDestinations`). **Envies du voyageur** (`trip.instructions`, 1000 caractères, facultatives, réutilisées à chaque génération et dans la discussion) : donnée non fiable, mêmes barrières que la discussion (`ATTACK_PATTERNS` → 400 `INSTRUCTIONS_REJECTED` sans appeler l'IA, balise `<envies>` = données, `INSTRUCTION_MARKERS` sur le planning produit) ; un titre recopié d'un récit est remplacé. **Nombre de voyageurs** (`trip.traveler_count`, 1 à `TRIP_MAX_TRAVELERS`) : budget pour tout le groupe, hébergement et rythme adaptés. **Carte** : un repère par ville **citée dans le planning** (seuls un trajet ou un hébergement déplacent le voyageur à plus de 80 km : un restaurant qui porte le nom d'une autre ville ne compte pas) (`findCitiesInText` : villes des pays du voyage dans country-state-city, nom propre avec majuscule, 4 lettres minimum, liste de mots courants exclus), avec ses jours sur place (un jour sans ville citée reste dans la dernière ville) ; recalculée à chaque lecture, donc à jour après toute modification. À défaut : séjours donnés par l'IA à la génération (`trip_stop`, coordonnées toujours calculées par le serveur), puis étapes choisies sans dates. Bulle : nom de la ville et dates seulement, insérés comme texte. **Heure locale** (pendant le voyage) : fuseau de la ville du jour de cette même liste (sinon du séjour `trip_stop`, sinon de la première étape), calculé hors ligne par `@photostructure/tz-lookup` (`timeZoneAt`, `location.service.ts`) ; pendant le voyage, cette heure de la destination remplit `<maintenant>` du prompt et prime sur l'heure de l'appareil (`clientTime`, juste seulement si le téléphone est à l'heure locale) ; avant et après le voyage, heure de l'appareil, sinon de Paris. **Temps libre** : minutes jusqu'à la prochaine activité du jour (sinon jusqu'à minuit) et dernière activité commencée (peut-être en cours) ; le planning n'a que des heures de début ; le trajet de l'activité commencée à la suivante est ajouté s'il est déjà en cache (`trajetVersProchaine`, `findCachedTravelBetween` : lecture seule, jamais d'appel à OpenRouteService), sinon Biirbou garde une marge. **Position** (`POST /trips/[id]/messages` : `position` GPS **ou** `place` « Je suis à… », 100 caractères) : demandée au navigateur uniquement au clic (`getRoughPosition`, Permissions-Policy `geolocation=(self)`), arrondie à 2 décimales (≈ 1 km) par le navigateur **et** par le schéma Zod, envoyée à Biirbou avec la ville la plus proche (`nearestCity`, 30 km au plus, hors ligne) et seulement pendant le voyage ; **jamais enregistrée ni loggée** (absente de `trip_message`). Le lieu écrit est une entrée non fiable : `ATTACK_PATTERNS` et balises neutralisées, comme le message. **« Que faire maintenant ? »** : bouton de la carte du copilote et du panneau Biirbou, affiché pendant le voyage seulement (`live` de `GET /trips/[id]`, null pour un lecteur) ; envoie le message « Que faire maintenant ? » avec le contexte du moment (`TripWhatNow.tsx`), la réponse et ses propositions d'ajout (acceptées une par une, annulables) arrivent dans le panneau, sur le quota habituel. **Énergie** (`energy` : `TRIP_ENERGY_LEVELS` tired / motivated / relaxed) : choisie dans « Que faire maintenant ? » ou « Adapter ma journée », envoyée à Biirbou sous un libellé fixe (jamais un texte du voyageur, dans `<maintenant>`), même hors du voyage, jamais enregistrée. **Imprévus** (« Adapter ma journée », `disruption` : `TRIP_DISRUPTIONS` rain / closed / late / cancelled / budget / wish, et le jour concerné, refusé hors des dates du voyage → 400) : motif choisi en puce, envoyé comme valeur connue et traduit par le serveur en libellé fixe (`imprevu` dans `<maintenant>`, avec des consignes par motif : ne toucher qu'aux activités concernées) ; la discussion affiche une phrase fixe suivie des précisions facultatives du voyageur (texte non fiable, comme tout message) ; la fatigue passe par l'énergie ; jamais enregistré. **Imprévu repéré** (#06, #08) : quand le message ou le motif signale un imprévu, Biirbou renvoie aussi `disruption` (résumé, durée si connue — jamais inventée —, jours, activités touchées avec la raison) ; donnée non fiable revérifiée par `checkedDisruption` (textes sur une ligne sans balise ni fuite des consignes, jours du voyage, activités de CE voyage une seule fois, sans jour : rien ; identique au dernier imprévu de l'historique sans motif choisi : rien, pas de carte répétée) puis gardée avec la réponse (`trip_message.disruption_*`, `trip_message_impact` : copie de l'activité, `item_id` null si elle est supprimée depuis). Affiché sous la réponse dans le panneau (carte « Imprévu repéré par Biirbou ») ; les activités touchées par le **dernier** imprévu de moins de 24 h (`impacts` de `GET /trips/[id]`) sont surlignées dans le planning avec la raison. **Replanification** (#10, #11), garantie par le serveur (`touchableItems`) quelle que soit la réponse de l'IA : une proposition ne modifie ni ne supprime jamais une activité **gardée** (`trip_item.pinned`, cadenas « Verrouiller » sur chaque activité, `PATCH …/items/[itemId]` `pinned`, ni « manuel » ni notification ; verrouillée, **personne** ne la modifie, ne la supprime ni ne change sa couleur, et « Annuler » ne la touche pas : 409 `ITEM_LOCKED`, vérifié dans la requête SQL d'écriture, seul `{ pinned: false }` passe ; l'interface ne montre que « Déverrouiller ») ni une activité **passée** pendant le voyage (avant la date et l'heure de `<maintenant>`, marquée « passée » dans `<planning>`, jamais « touchée »), et rien ne s'ajoute dans un créneau passé ; après un imprévu (repéré ou motif), seulement les activités touchées ou celles des jours de l'imprévu encore à venir. Biirbou propose la suite de la journée en un lot ; « Tout accepter » (`POST /trips/[id]/messages/[messageId]/accept`) applique les propositions en attente d'une réponse en une transaction et un seul changement annulable (`trip_plan_change.suggestion_ids`) ; une proposition périmée (activité disparue ou gardée depuis) est refusée sans bloquer les autres. **Avant / après** (#12) : sous chaque réponse avec des propositions en attente, « Voir l'avant / après » montre les jours concernés avant et après (ajoutée, modifiée, déplacée, retirée, gardée), calculé dans le navigateur à partir du planning affiché, sans appel au serveur ni à l'IA ; lecture seule pour un lecteur. Les activités gardées restent aussi quand Biirbou re-génère un jour ou réimagine le voyage (`<gardees>` dans le prompt, planning construit autour).
- **Temps de trajet** (`GET /trips/[id]/days/[day]/travel`, `trip-travel.service.ts`, pass voyage, lecteur compris, `RATE_LIMIT_TRIP_TRAVEL_*`) : **OpenRouteService** (données OpenStreetMap, clé `ORS_API_KEY` lue par `getRoutingConfig()`, absente ou invalide : seuls les trajets sont coupés), appelé par le serveur uniquement, réponses revalidées par Zod, 5 s max. Lieu d'une activité (jamais une ville, une région ou un pays entiers : leur centre fausserait le trajet) : nom donné par Biirbou (`trip_item.place_name`, champ `placeName` des prompts, nettoyé comme toute sortie de l'IA ; effacé si le titre change à la main), sinon mots distinctifs du titre (aucun : pas d'appel) ; cherché autour de la ville du jour (`tripDayAreas`, 30 km, pays), lieu précis avant quartier, accepté seulement si son nom correspond (`placeNameMatches`). Gardé en base (`place_query` = recherche faite, coordonnées null = introuvable) : nouvelle recherche seulement si titre, lieu ou ville du jour changent ; 8 recherches par appel. Tronçons entre activités consécutives (un transport coupe la journée), à pied et en voiture au-delà de 1,5 km à vol d'oiseau ; pas de transports en commun ni de trafic (dit à l'écran). Cache partagé `travel_leg` (deux points arrondis à 4 décimales et un mode, aucune donnée personnelle ; `brb_app` : lecture et ajout seulement). **Plafond de tout le site** (`ORS_GEOCODE_*_MAX`, `ORS_MATRIX_*_MAX`, par jour et par minute, défauts à 90 % du plan gratuit : 3 000 recherches et 500 calculs par jour), compteurs en mémoire : au-delà de 80 % du plafond du jour, seul le jour en cours d'un voyage en cours (`liveTripDay`) lance encore des appels ; la marche passe avant la voiture. Plafond atteint, panne, délai ou 429 : **jamais d'erreur pour le voyageur**, les trajets en cache sont renvoyés avec `deferred: true` (« Certains temps de trajet arriveront plus tard »), les lieux non cherchés restent en attente (jamais marqués introuvables) ; un log `routing` par jour quand un plafond est atteint. Seule la clé absente donne 503 `TRAVEL_UNAVAILABLE`. Mention des sources obligatoire (licences OpenRouteService et OpenStreetMap) : derrière l'icône ⓘ de « Trajets estimés… », jamais supprimée. OpenRouteService ne reçoit que des noms de lieux et des coordonnées (politique de confidentialité).
- **Déplacements** (génération, jour re-généré, discussion) : villes de base (2 nuits au moins), excursions à la journée (moins de 2 h environ, retour le soir), une ville où l'on dort = un seul bloc de jours (sauf boucle finale vers la ville d'arrivée ou envie explicite), train ou bus jusqu'à 5 h environ, avion au-delà ou pour la mer ; chaque trajet entre bases est une activité transport (mode, départ → arrivée, durée). **Liens** : l'IA ne cite que les noms de `transportsOfficiels` (`lib/transport.ts`, liste fixe de sites officiels) et jamais d'URL ; toute adresse web écrite par l'IA est retirée (`withoutLinks`) ; le planning affiche lui-même les liens de la liste.
- **Météo** (`GET /trips/[id]/weather`, `weather.service.ts`, gratuit, lecteur compris, `RATE_LIMIT_TRIP_WEATHER_*`) : **MET Norway** (api.met.no, gratuit y compris en usage commercial, sans clé, licence CC BY 4.0 : source affichée sous la météo, jamais supprimée ; Open-Meteo écarté, gratuit seulement hors usage commercial). Appelé par le serveur uniquement, User-Agent identifiant l'app (adresse du site), coordonnées de la ville du jour arrondies à 2 décimales, réponses revalidées par Zod, 5 s max, cache mémoire jusqu'à `Expires`. Seulement les jours couverts par les prévisions (environ 9 jours) : au-delà rien n'est affiché ni estimé. Panne : « Prévisions météo indisponibles » (log INFO, pas d'alerte). Envoyée à Biirbou dans `<meteo>` (libellés fixes, jamais un texte du service), au plus 2,5 s d'attente : sans elle, il parle de la saison.
- **Suppression du compte** (#112, `DELETE /api/v1/users/me`, par son titulaire, mot de passe exigé, rate limit du login ; un admin doit d'abord être rétrogradé) et par un admin : même transaction `deleteAccount` (user.repository). Chaque voyage partagé passe au plus ancien éditeur (sinon lecteur) non banni ; les autres voyages, récits, photos (bucket), likes et sessions sont supprimés ; le nom reste sur les lignes de dépenses des autres voyages (`trip_participant.name`), pass voyage et dons restent sans lien (`on delete set null`). Trace : log INFO avec l'identifiant (qui ne désigne plus personne).
- **Modération** (`moderation.service.ts`, `server/moderationFilter.ts`) : **texte** (récits et commentaires) vérifié sans IA par une liste de mots bannis (injures, haine, sexuel explicite, appels à voter ; leet et séparateurs décodés) ; les avis négatifs et jurons d'exclamation restent autorisés. **Photo** d'un récit vérifiée par Gemini, réduite à 384 px (coût minimal). Refus → rien n'est enregistré ; l'auteur voit seulement « ne respecte pas les règles » (motif dans les logs serveur, pour ne pas dévoiler la liste). IA coupée ou en panne → récit publié masqué en attente de validation admin (`pending_review`, non réaffichable par l'auteur).
- **Mot de passe oublié** : email via **Gmail en SMTP** (`server/infra/mailer.ts`, nodemailer, TLS 465, mot de passe d'application `SMTP_PASSWORD`, jamais celui du compte ; config `getMailConfig()` validée à part : absente ou invalide, seuls les emails sont coupés). Réponse identique (202, au moins 2 s) que le compte existe ou non ; rate limit par IP **et** par email visé. Lien construit **uniquement** avec `APP_URL` en production (jamais l'en-tête Host), code dans le fragment `#token=` (absent des logs d'accès), 32 octets aléatoires, seule l'empreinte SHA-256 en base (`password_reset_token`), usage unique, `PASSWORD_RESET_TTL_MINUTES`, un seul lien ouvert par compte. Reset : bcrypt, toutes les sessions révoquées ; jamais pour un compte banni. Mail en texte brut (`messages/fr.json`), aucun HTML.
- **Assignés du Kanban** (`support_ticket_assignee`, `dev_ticket_assignee`) : plusieurs admins par ticket (`TICKET_MAX_ASSIGNEES`), liste complète envoyée dans le PATCH du ticket (`assigneeIds`, remplace la précédente dans une transaction, ticket verrouillé). Admins actifs uniquement (revérifié en base) ; un admin rétrogradé ou banni n'est plus affiché, et disparaît au prochain changement. Jamais renvoyé à l'auteur d'un ticket de support. Ajouts / retraits inscrits au journal `admin_action`.
- **Tickets de support** (`support_ticket`) : ouverts par un utilisateur connecté non banni (sujet 3–120, message 10–2000 caractères, `RATE_LIMIT_TICKET_*`), visibles par leur auteur et les admins uniquement. État `open` → `in_progress` → `resolved` → `closed` (colonnes À faire, En cours, Fait, Clôturé du Kanban), changé uniquement par un admin (onglet Kanban, tableau Support, inscrit au journal `admin_action`) et visible aussitôt par l'auteur sur sa page Support. Le texte d'un ticket n'est jamais modifié. Le Kanban charge tous les tickets non clôturés (priorité haute d'abord) et les 30 derniers clôturés. **Priorité** (`priority`, basse / moyenne / haute, type `ticket_priority` partagé avec les tickets de développement) : réservée aux admins, jamais renvoyée à l'auteur.
- **Tickets de développement** (`dev_ticket`) : tableau Développement du Kanban, pour les améliorations de Biirb. Écrits, modifiés, déplacés (`todo`, `in_progress`, `done`, `closed`) et supprimés par les admins uniquement (`requireAdmin`, journal `admin_action`) ; jamais visibles hors de l'administration. Titre 3–120, description facultative ≤ 2000, priorité basse / moyenne / haute.
- **Support** (`support_ticket`) : catégorie obligatoire (`TICKET_CATEGORIES` : trip_pass, bug, report, account, other). `trip_pass` envoie un email à tous les admins actifs (un par admin, texte fixe sans le message de l'utilisateur, jamais bloquant pour le ticket). Le lien support de la fenêtre du pass pré-remplit la demande (`/support?topic=trip_pass&trip=<uuid>`).
- **Commentaires** (`post_comment`) : lecture publique (exception GET dans `proxy.ts`), écriture réservée aux connectés non bannis, filtrés par la liste de mots bannis. Fils à un seul niveau (`parent_id` : on répond à un commentaire principal, pas à une réponse). Suppression par l'auteur ou un admin (journal).
- **Administration** : seul le rôle `admin` donne des droits ; les autres rôles sont des badges. Le rôle est **relu en base à chaque requête** (`requireAdmin`), jamais lu dans le JWT ni dans la session du navigateur (le lien « Administration » de la Navbar n'est qu'un affichage). Un admin ne peut ni se rétrograder, ni se bannir, ni se supprimer, ni bannir / supprimer un autre admin sans l'avoir rétrogradé. Toute action admin modifiante est inscrite au journal `admin_action`. La liste des utilisateurs de l'admin n'expose jamais d'email ni de hash.
- **Bannissement** : connexion refusée (`ACCOUNT_BANNED`, révélé seulement après un mot de passe correct), refresh refusé, sessions révoquées ; l'access token en cours reste valide au plus 1 h, mais l'IA, les signalements et l'admin relisent le compte en base.
- Discussion IA d'un voyage (`/trips/[id]/messages`) : enthousiaste pour toute envie liée au voyage (l'IA cherche où et quand la caser), impassible sur le reste. Trois barrières contre l'injection (`trip.service.ts`) : 1) filtre d'entrée déterministe (`ATTACK_PATTERNS` : « ignore tes instructions / la sécurité », jailbreak, balises / champs du prompt, « nouvelle règle : … », « désormais tu réponds… », « réponds en anglais »…) → refus sans appeler l'IA ; 2) consignes du modèle (contenu utilisateur = données, règles confidentielles, illégal refusé, toujours en français : aucune consigne de langue, de ton ou « pour la suite » venant d'un message, rappelé à la fin du prompt) ; 3) filtre de sortie (`INSTRUCTION_MARKERS`, et `notFrench` : réponse surtout en anglais) → une réponse qui laisse fuiter les consignes ou suit une consigne du voyageur est bloquée. Un échange refusé ou bloqué passe hors sujet : il n'est plus renvoyé dans l'historique, la consigne ne persiste pas. **Copilote** (`TripCopilot.tsx`) : le prompt reçoit aussi `<maintenant>` (date et heure de l'appareil, `clientTime`, ignorée à plus de 15 min de l'heure du serveur → heure de Paris ; jour N du voyage), `<budget>` (prévu, converti dans la devise du voyage, et dépensé) et `<memoire>` (`trip.memory`, 600 caractères : contraintes durables réécrites par l'IA dans la même réponse, champ `memory` ; filtrée par `ATTACK_PATTERNS` / `INSTRUCTION_MARKERS` avant d'être enregistrée, vide ou suspecte → l'ancienne est gardée ; corrigée ou effacée par les éditeurs via PATCH, même filtre ; ajoutée aux envies des générations). Provenance des activités (`trip_item.origin` : `ai` génération ou proposition acceptée, `manual` ajout ou modification du contenu à la main) : badge sur chaque activité, et l'IA ne touche pas aux activités « manuel » sans demande. Tout changement du prompt se vérifie avec une batterie d'attaques (injection directe, via un récit, jailbreak, fuite, données d'autres utilisateurs, consigne glissée dans la mémoire). Hors sujet non renvoyé dans l'historique, message ≤ 500 caractères, historique court, 30 messages/heure/utilisateur et 50 par voyage. L'IA peut proposer d'ajouter, de modifier ou de supprimer une activité (`trip_suggestion.action`, `target_item_id` : id lu dans le planning du prompt, revérifié comme appartenant au voyage) ; rien ne change sans un « oui » de l'utilisateur, proposition par proposition (activité disparue entre-temps → 409 `SUGGESTION_OUTDATED`).
- **Annuler un changement de Biirbou** (`trip_plan_change`, `POST /trips/[id]/undo`) : proposition acceptée (seule, ou toutes celles d'une réponse avec « Tout accepter » : remises en attente ensemble), re-génération complète ou d'un jour, annulables pendant `TRIP_UNDO_HOURS` (24 h), **le plus récent d'abord**, par un éditeur ou le propriétaire. Dans la même transaction que le changement (voyage verrouillé) : photo du planning avant (activités ; tout ce que la re-génération remplace : checklist, séjours, budget, note de saison) et empreinte du contenu après (jamais les ids ; sans l'état « fait » de la checklist ni l'épingle). La photo garde aussi les ids des activités et les liens qui les visent (`trip_suggestion.target_item_id`, `trip_message_impact.item_id`, mis à null par la suppression) : « Annuler » remet chaque activité sous son id d'origine (jamais réutilisé par l'identité, `overriding system value`), sans toucher à celles qui n'ont pas changé, puis relie de nouveau propositions et imprévus ; une proposition remise en attente reste donc acceptable. Une activité encore là garde son épingle (choix du voyageur, pas de Biirbou) ; version incrémentée si son contenu change. Photo sans ids (avant cette correction) : activités recréées avec de nouveaux ids. Empreinte différente au moment d'annuler = planning modifié à la main depuis → 409 `PLAN_CHANGED`, rien n'est restauré. Proposition annulée → remise en attente. La génération initiale n'est pas enregistrée ; historique de plus de 24 h purgé au changement suivant. `GET /trips/[id]` renvoie `undo` (null pour un lecteur).
- **Identifiant d'un voyage** : la clé `trip.id` (entier) reste interne aux clés étrangères et ne sort jamais du serveur ; URL, API, admin et support utilisent `trip.public_id` (UUID, `tripIdParamSchema`), converti au début de chaque controller par `resolveTripId` (inconnu → 404).
- **Voyages partagés** : le propriétaire (`trip.user_id`) invite par pseudo exact (acceptation requise) ou par lien (`/planner/join#<code>`, 7 jours, réutilisable, révocable ; seule l'empreinte SHA-256 du code est stockée). **10 voyageurs maximum** par voyage (`TRIP_MAX_TRAVELERS` : propriétaire + membres + participants sans compte), vérifié dans la même transaction que l'ajout (verrou sur le voyage), 409 `TRIP_FULL`. Rôles : `owner` (tout, dont supprimer le voyage et gérer les membres), `editor` (planning, dépenses, discussion IA, sur son propre quota), `viewer` (consultation ; ne saisit et ne modifie que ses propres dépenses). Droits vérifiés par `requireTripRole` (`trip-access.service.ts`) dans chaque service : pas d'accès → 404, accès insuffisant → 403.
- **Synchronisation entre membres** : la page d'un voyage (planning, discussion, dépenses) se relit toutes les 30 s et au retour sur l'onglet (`useLiveRefresh`, onglet visible et en ligne seulement) ; une relecture partie avant une modification n'écrase pas son résultat. **Conflits** : titre, budget et activités portent une `version` ; le client renvoie celle lue au début de la saisie dans `If-Match` (PATCH du voyage, PATCH / DELETE d'une activité), le serveur répond 412 `CONFLICT` sans rien modifier si elle est périmée, et l'utilisateur choisit entre la version enregistrée et la sienne (`TripConflictDialog`). Sans `If-Match` : dernière écriture gagnante. La mémoire de Biirbou n'incrémente pas la version du voyage.
- **Notifications** (`notification`, `notification.service.ts`) : changement du programme par un membre (re-génération, jour re-généré, annulation, proposition acceptée, activité ajoutée / modifiée / retirée, titre ou budget ; pas la couleur ni la checklist) → une notification pour chacun des autres membres, jamais bloquante pour le changement. Même changement répété dans les 10 minutes et non lu : une seule. Visibles seulement par leur destinataire et tant qu'il est membre du voyage, gardées 30 jours, toutes marquées lues à l'ouverture de la cloche, effaçables par leur destinataire (« Tout effacer »). Détail (titre d'activité) affiché comme texte. **Hors de l'app**, au choix de chaque membre et voyage par voyage (`trip_notification_setting`, cases décochées par défaut, bouton « Notifications » du voyage) : **navigateur** (push web **en suspens** : code prêt mais clés VAPID non déployées, la case affiche « Pas encore disponible » ; pour l'activer : secrets `brb-vapid-public-key` / `brb-vapid-private-key` dans Secret Manager + `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` (`--set-secrets`) et `VAPID_SUBJECT` dans `deploy.yml` ; `web-push`, clés via `getPushConfig()`, autorisation demandée seulement au clic, un abonnement par appareil dans `push_subscription`, adresse limitée aux services de push des navigateurs contre le SSRF, supprimé à la déconnexion ou si le service le refuse ; le service worker n'ouvre que `/planner/<uuid>`) et **email** (Gmail SMTP, texte fixe **sans aucun texte saisi par un membre** : seulement le type de changement et le lien `APP_URL`). Envoyés seulement pour une notification réellement créée (anti-doublon compris), jamais à un compte banni, sans jamais bloquer le changement.
- **Dépenses (Tricount)** : participants = comptes du voyage + invités sans compte. Montants en unités mineures de leur devise (0 décimale : JPY, KRW, ISK) ; conversion dans la devise du voyage au taux BCE du jour de la dépense (`server/infra/exchangeRates.ts`, API Frankfurter, sans clé), **taux figé** à la saisie. Parts calculées au centime (plus forts restes, somme exacte). Affichage des comptes dans une autre devise du voyage (`?display=`, devise du voyage ou d'une dépense) : chaque dépense au taux BCE **du jour où elle a été payée** (`getEuroRates` : une table en base euro par jour, gardée en mémoire, A → B = table[B] / table[A] ; montant exact si elle a été payée dans cette devise), parts au plus fort reste ; « marquer comme remboursé » seulement dans la devise du voyage, qui fait foi ; budget prévu (saisi en euros) au dernier taux. Équilibrage = minimum de virements ; « marquer comme remboursé » crée une dépense de remboursement. Devise du voyage modifiable tant qu'aucune dépense n'existe.
- **Consentements** (`src/lib/legal.ts`, pages `/legal/{terms,sales,notice,privacy}`, textes dans `messages/fr.json` → `Legal`) : CGU à l'inscription (`users.terms_version` / `terms_accepted_at`), CGV + renonciation au droit de rétractation avant le lien de paiement du pass (commande, puis copiés dans `trip_pass`). - **Pass voyage** (9,99 € par défaut, `BMC_TRIP_PASS_*`) : article « Extra » Buy Me a Coffee, **par voyage**, profite à tous ses membres. Le propriétaire commande (`trip_pass_order`, 24 h, une par compte) puis paie avec l'email de son compte ; le webhook signé `extra_purchase.created` (bon article, montant ≥ prix, en euros) crée le `trip_pass` ; `extra_purchase.refunded` le retire. Le lien de paiement n'apparaît qu'après avoir confirmé payer avec l'email du compte. Achat sans compte ou sans commande : gardé « à rattacher » (`trip_id` null, jamais perdu) ; email du paiement jamais en clair (empreinte HMAC + aperçu masqué). L'admin (onglet Pass voyage) rattache un achat seulement si l'email déclaré par l'acheteur correspond à l'empreinte, offre ou retire un pass (journal). Débloque : quota IA plus haut sur ce voyage (`AI_DAILY_LIMIT_TRIP_PASS`, 100 par jour) et discussion de 200 messages, re-générer un jour, export PDF et .ics, liens Google Maps par jour. Le pass est **toujours vérifié côté serveur** (`requireTripPass`, 402 `PASS_REQUIRED`) : l'interface ne fait qu'afficher. Le rôle mécène reste réservé aux dons.
- **Mesure d'audience** : **Umami Cloud** (sans cookie ni stockage dans le navigateur, respecte Do Not Track), balise dans `layout.tsx` si `UMAMI_WEBSITE_ID` (`getAnalyticsConfig()`, lue au build : argument du build Docker **et** variable Cloud Run). Query et fragment de l'URL jamais envoyés (`data-exclude-search`, `data-exclude-hash` : recherches, UUID de voyage, code d'invitation, code du mot de passe oublié), domaine limité à `APP_URL`. Jamais d'email, de pseudo ni d'identifiant dans un événement. Événements serveur : `trackServerEvent` (`analytics.service.ts`), sans IP ni User-Agent du visiteur, attendus (2 s max) mais jamais bloquants ; User-Agent fixe qui passe le filtre anti-robots d'Umami (sinon ignorés sans erreur). Revenu : données `revenue` + `currency`.
- **Hors ligne (PWA)** : `public/sw.js` (production uniquement) met en cache les pages `/planner*`, les GET `/api/v1/trips*` et les fichiers `/_next/static` ; consultation seule. Pages et données ne sont gardées qu'avec « Se souvenir de moi » (repère `brb-remembered` posé par `session.ts`, sinon purgées et jamais servies) ; vidées à la déconnexion et au changement de compte.
